# Pillar P07 — Forms

**Status**: Draft · **Owner**: Platform team · **Updated**: 2026-08-31

> Dynamic data collection, both for case creation and for in-case data entry, with versioning.

## 1. Pillar statement

This pillar owns **forms**: declarative, versioned definitions of how structured data is collected from users. A form is bound to a case type (P01) and renders fields according to the case type's schema (P05) plus form-specific layout, conditional visibility, and validation rules. A form has a lifecycle (draft → published → retired) and is immutable on publish.

A form is not a "screen". It is a **declarative specification** that the UI renders. The pillar guarantees:

- forms are versioned and immutable on publish,
- forms are bound to a case type version, not to a case,
- a form can include layout, conditional sections, and form-level validation,
- a form can hide or require fields based on the case's current state or data,
- a form's submission produces the same data the case type's schema expects (validation is shared with P05).

## 2. Scope

### In scope
- Form definition format: sections, fields, layout hints, conditional visibility, form-level validation.
- Form lifecycle: draft → published → retired; immutable on publish.
- Form binding to a case type version.
- Form-level validation (e.g., "if `hasSpouse` is true, `spouseName` is required").
- Conditional visibility: show/hide fields based on other field values or case state.
- Form rendering: server-rendered HTML in v1; client-rendered SPA later.
- Form submission → case data with the same validation as direct case creation.

### Out of scope (deferred)
- A drag-and-drop form designer UI. (P3; first slice ships JSON.)
- Custom widgets beyond standard HTML inputs. (P3; first slice uses standard inputs only.)
- Multi-page forms with separate URLs. (P3; v1 is single-page.)
- Form analytics (drop-off, time-to-complete). (P3; P12 territory.)

### Explicitly not building
- A "form" that is actually code-generated by the UI. Forms are declarative.
- A form engine that runs arbitrary JavaScript. v1 uses standard HTML inputs with declarative visibility and validation.

## 3. Primary entities

| Entity | Purpose | First slice |
|---|---|---|
| `FormDefinition` | A versioned form specification. | Deferred (P3 priority) |
| `FormVersion` | An immutable, published snapshot. | Deferred |
| `FormBinding` | The link between a FormVersion and a CaseTypeVersion. | Deferred |
| `FormField` | A field on a form (referencing a FieldDefinition by key). | Deferred |
| `FormSection` | A grouping of FormFields. | Deferred |
| `ConditionalRule` | A declarative visibility / requiredness rule. | Deferred |
| `FormSubmission` | The data submitted via a form. | Deferred |

## 4. User stories (priority-tiered)

### P1 — Critical
- **P07-US1**: As an intake user, I can fill out a published form for a case type, and the submitted data creates a case with the form's data validated against the case type's schema.

### P2 — Important
- **P07-US2**: As a process administrator, I can define a form with sections, fields, and conditional visibility (e.g., "if `isAppeal = true`, show `appealReason`"), and publish it as a new version.
- **P07-US3**: As an intake user, when a field on the form is hidden by a conditional rule, the field's data from a previous submission is preserved but the field is not re-submitted.
- **P07-US4**: As a process administrator, I can bind a form version to a case type version, and the binding is immutable on publish.

### P3 — Deferred
- **P07-US5**: As a process administrator, I can use a drag-and-drop form designer; the designer emits the same form definition format.
- **P07-US6**: As a case worker, I can complete a multi-step form with progress saved at each step.
- **P07-US7**: As a process administrator, I can attach a form to a workflow state, so the form renders when a transition is requested.

## 5. Cross-cuts

- **P01 (Case)**: form submission produces a case (or updates a case) with the data validated by P01.
- **P05 (Metadata)**: form fields reference FieldDefinitions by stable machine key.
- **P10 (Administration)**: forms are configuration artifacts owned by P10.
- **P11 (Security)**: form access can be role-restricted.

## 6. Acceptance scenarios (representative)

- G1: A published form for a case type accepts a submission; the data is validated against the case type's schema; the case is created with the submitted data.
- G2: A form has a conditional rule: when `isAppeal = true`, `appealReason` is required. Submitting with `isAppeal = true` and no `appealReason` is rejected with a structured error identifying the field.
- G3: A form is published. A process administrator attempts to modify it. The system rejects the modification; a new version is required.
- G4: A form bound to case type version 1 is used to submit a case. A new form version bound to case type version 2 is published. Existing cases retain their form data; new submissions use the new form.

## 8. Open questions

- Q1: Is a "form" always bound to a case type, or can it be a standalone data-collection surface? (Current intent: v1 always bound to a case type; standalone forms are P3.)
- Q2: Can a form be embedded in an external system? (Current intent: yes via API; the form definition is exposed, the rendering is the consumer's responsibility.)
- Q3: How are form attachments (file uploads within a form) handled? (Current intent: they are document uploads via P03; the form is metadata-only.)
